## Incident 1 — Terraform Cannot Assume IAM Role

### Error
```
Error: Cannot assume IAM Role
IAM Role (arn:aws:iam::725094769583:role/for-payflow-terraform) cannot be assumed.
User: arn:aws:sts::725094769583:assumed-role/payflow-dev-bastion-role/i-046378ebbb7ae6710
is not authorized to perform: sts:AssumeRole on resource:
arn:aws:iam::725094769583:role/for-payflow-terraform
```

### Root Cause
Two-sided misconfiguration:
1. The trust policy on `for-payflow-terraform` referenced a stale/deleted role ID (`AROA2RUYEEOXXOZFVJAVY`) instead of the bastion role ARN.
2. Needed to verify the bastion role had an inline policy granting `sts:AssumeRole`.

### Investigation
```bash
# Check trust policy on the target role
aws iam get-role --role-name for-payflow-terraform

# Check bastion role policies
aws iam list-role-policies --role-name payflow-dev-bastion-role
aws iam list-attached-role-policies --role-name payflow-dev-bastion-role

# Inspect the inline policy content
aws iam get-role-policy \
  --role-name payflow-dev-bastion-role \
  --policy-name AssumeTerrformRole
```

### Findings
- Trust policy on `for-payflow-terraform` had a raw role ID (stale principal from a deleted role) — IAM silently rejects these.
- Bastion already had inline policy `AssumeTerrformRole` granting `sts:AssumeRole` on the correct ARN ✅

### Fix
Updated the trust policy on `for-payflow-terraform` to use the bastion role ARN:

```bash
aws iam update-assume-role-policy \
  --role-name for-payflow-terraform \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::725094769583:role/payflow-dev-bastion-role"
      },
      "Action": "sts:AssumeRole"
    }]
  }'
```

### Verification
- `aws iam get-role --role-name for-payflow-terraform` confirmed trust policy now references the correct ARN.
- `aws iam get-role-policy --role-name payflow-dev-bastion-role --policy-name AssumeTerrformRole` confirmed permission exists on the bastion side.

## Incident 2 — Kubernetes Cluster Unreachable (Helm Releases Timing Out)

### Error
```
Error: Kubernetes cluster unreachable:
Get "https://42490B50986B189204F7CF385E886004.gr7.us-east-1.eks.amazonaws.com/version":
dial tcp 10.1.30.88:443: i/o timeout

Affected resources:
- module.eks_addons.helm_release.alb_controller
- module.eks_addons.helm_release.metrics_server
- module.eks_addons.helm_release.cluster_autoscaler
```

### Root Cause
The EKS cluster API endpoint is **private-only** (`endpointPublicAccess: false`). The bastion and EKS cluster are in **different VPCs** connected via Transit Gateway. Routing was correctly configured, but the **EKS cluster security group had no inbound rule for port 443** from the bastion VPC CIDR, causing TCP-level timeouts.

### Investigation
```bash
# Confirm EKS endpoint access mode
aws eks describe-cluster --name payflow-eks-dev \
  --query 'cluster.resourcesVpcConfig.{public:endpointPublicAccess,private:endpointPrivateAccess,vpc:vpcId}'

# Check bastion VPC
aws ec2 describe-instances \
  --filters "Name=iam-instance-profile.arn,Values=arn:aws:iam::725094769583:instance-profile/*bastion*" \
  --query 'Reservations[0].Instances[0].{VpcId:VpcId,SG:SecurityGroups}'

# Confirmed different VPCs:
#   Bastion VPC:  vpc-091ab54e958db621d (10.0.0.0/16)
#   EKS VPC:      vpc-0a90ed74659b3dc95 (10.1.0.0/16)

# Check Transit Gateway attachments
aws ec2 describe-transit-gateway-attachments \
  --filters "Name=transit-gateway-id,Values=tgw-0225572ee858b7cb3"

# Check route tables in both VPCs
aws ec2 describe-route-tables \
  --filters "Name=vpc-id,Values=vpc-0a90ed74659b3dc95"
aws ec2 describe-route-tables \
  --filters "Name=vpc-id,Values=vpc-091ab54e958db621d"

# Check EKS cluster security group inbound rules
aws ec2 describe-security-groups --group-ids sg-0d77a8ba578391d69
```

### Findings
| Check | Result |
|---|---|
| EKS endpoint | Private only (`endpointPublicAccess: false`) |
| VPCs | Different — bastion `10.0.0.0/16`, EKS `10.1.0.0/16` |
| TGW attachments | Both VPCs attached ✅ |
| Route tables | `10.1.0.0/16 → TGW` in bastion VPC ✅, `10.0.0.0/16 → TGW` in EKS VPC ✅ |
| EKS cluster SG inbound | Only self-referencing rule — **no port 443 from bastion VPC** ❌ |

### Fix
Added inbound rule to EKS cluster SG allowing TCP 443 from the bastion VPC CIDR:

```bash
aws ec2 authorize-security-group-ingress \
  --group-id sg-0d77a8ba578391d69 \
  --ip-permissions '[{
    "FromPort": 443,
    "IpProtocol": "tcp",
    "IpRanges": [{"CidrIp": "10.0.0.0/16", "Description": "Allow bastion VPC to reach EKS API"}],
    "ToPort": 443
  }]'
```

### Verification
- `aws ec2 describe-security-groups --group-ids sg-0d77a8ba578391d69` confirmed new inbound rule `sgr-0adf4bd78ca1cccb7` is active.

### Terraform Codification
To prevent recurrence, added `aws_security_group_rule` to `modules/eks/main.tf` controlled by a new `bastion_vpc_cidr` variable, wired through `platform/infra/main.tf`, `variables.tf`, and `terraform.tfvars` (`bastion_vpc_cidr = "10.0.0.0/16"`). Import command to bring existing rule into state:
```bash
terraform import \
  'module.eks.aws_security_group_rule.cluster_api_from_bastion_vpc[0]' \
  'sg-0d77a8ba578391d69_ingress_tcp_443_443_10.0.0.0/16'
```

## Incident 3 — Stale Terraform State Lock

### Error
```
Error: Error acquiring the state lock
ConditionalCheckFailedException: The conditional request failed
Lock Info:
  ID:        bf9cfb9b-76b9-d8cf-f887-a1fca1529823
  Path:      payflow-tfstate-003/dev/platform-addons/terraform.tfstate
  Operation: OperationTypeApply
  Created:   2026-04-01 22:00:45
```

### Root Cause
A previous `terraform apply` run was interrupted and never released the DynamoDB state lock.

### Investigation
```bash
aws ssm get-command-invocation \
  --command-id 7733ee78-df97-4387-9524-92903de4169b \
  --instance-id i-046378ebbb7ae6710
# StandardErrorContent revealed the lock error
```

### Fix
```bash
aws dynamodb delete-item \
  --table-name payflow-tfstate-lock \
  --key '{"LockID": {"S": "payflow-tfstate-003/dev/platform-addons/terraform.tfstate"}}'
```

### Verification
Subsequent `terraform apply` acquired the lock successfully.

## Incident 4 — Kubernetes Cluster Unreachable (Credentials Rejected)

### Error
```
Error: Kubernetes cluster unreachable: the server has asked for the client to provide credentials
Affected: helm_release.alb_controller, metrics_server, cluster_autoscaler, prometheus, grafana, loki, promtail, kubecost
```

### Root Cause
Two issues:
1. `platform/addons/providers.tf` had no `kubernetes` or `helm` provider configuration — providers were unconfigured.
2. `for-payflow-terraform` (the role Terraform assumes) had no EKS access entry, so its token was rejected by the cluster even after provider config was added.

### Investigation
```bash
# Confirmed providers.tf only had aws provider block
cat terraform/environments/dev/platform/addons/providers.tf

# Confirmed for-payflow-terraform not in access entries
aws eks list-access-entries --cluster-name payflow-eks-dev
```

### Fix
1. Added `kubernetes` and `helm` provider blocks to `providers.tf` using `aws_eks_cluster` and `aws_eks_cluster_auth` data sources.
2. Created EKS access entry for `for-payflow-terraform` with `AmazonEKSClusterAdminPolicy`:
```bash
aws eks create-access-entry \
  --cluster-name payflow-eks-dev \
  --principal-arn arn:aws:iam::725094769583:role/for-payflow-terraform \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name payflow-eks-dev \
  --principal-arn arn:aws:iam::725094769583:role/for-payflow-terraform \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster
```

### Terraform Codification
Set `terraform_user_arn = "arn:aws:iam::725094769583:role/for-payflow-terraform"` in `platform/infra/terraform.tfvars` to let the existing `aws_eks_access_entry.terraform_user` block own the entry. Import to avoid conflict:
```bash
terraform import \
  'module.eks.aws_eks_access_entry.terraform_user[0]' \
  'payflow-eks-dev:arn:aws:iam::725094769583:role/for-payflow-terraform'

terraform import \
  'module.eks.aws_eks_access_policy_association.terraform_user_admin[0]' \
  'payflow-eks-dev#arn:aws:iam::725094769583:role/for-payflow-terraform#arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy'
```

## Incident 5 — Helm Release Failures (ALB Webhook, Loki/Prometheus Timeout, Kubecost clusterId)

### Errors
```
1. Internal error: failed calling webhook "mservice.elbv2.k8s.aws": no endpoints available
   (prometheus, grafana, loki, promtail, kubecost)

2. context deadline exceeded
   (prometheus, loki)

3. execution error: clusterId is required. Please set .Values.global.clusterId
   (kubecost)
```

### Root Cause
1. **ALB webhook**: Monitoring helm releases deployed in parallel with `alb_controller`. The ALB controller pod wasn't ready yet, so its mutating webhook had no endpoints.
2. **Timeout**: Prometheus and Loki had `persistentVolume.enabled: true` with no `storageClass` specified. PVCs stayed pending because no default StorageClass was set on the cluster (EBS CSI is installed but `gp2` was not marked as default).
3. **Kubecost**: Newer chart version requires `global.clusterId` in addition to `kubecostProductConfigs.clusterName`.

### Investigation
```bash
# Check pod status in monitoring namespace
kubectl -n monitoring get pods
kubectl -n monitoring describe pod <pending-pod>
# Events showed: "no persistent volumes available for this claim and no storage class is set"

# Check StorageClasses
kubectl get storageclass
```

### Fix
1. Added `depends_on = [helm_release.alb_controller]` to all monitoring helm releases in `modules/eks_addons/main.tf`.
2. Added `storageClass: gp2` to `prometheus-values.yaml` and `loki-values.yaml`.
3. Added `global.clusterId: payflow-eks-dev` to `kubecost-values.yaml`.

If `gp2` is not marked as default StorageClass, set it:
```bash
kubectl patch storageclass gp2 \
  -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
```

## Incident 6 — Helm Values File Path Resolution Failure

### Error
```
Error: Invalid function argument
var.prometheus_values_path is "./../../../../k8s/helm-values/monitoring/prometheus-values.yaml"
no file exists at "./../../../../k8s/helm-values/..."
```

### Root Cause
`file()` inside the `eks_addons` module resolves paths relative to the module directory, not the calling environment. The relative `path.root` expression evaluated correctly in the environment but produced a relative string that was invalid from the module's working directory.

### Fix
Wrapped all values path arguments in `abspath()` in `platform/addons/main.tf`:
```hcl
prometheus_values_path = abspath("${path.root}/../../../../k8s/helm-values/monitoring/prometheus-values.yaml")
```

## Incident 7 — Insufficient IAM Permissions on `for-payflow-terraform`

### Root Cause
`for-payflow-terraform-dev` policy (v2) only covered EKS, basic IAM, EC2 describe, S3/DynamoDB state. Missing permissions for all workload and platform resources.

### Missing Permissions Identified
| Layer | Missing |
|---|---|
| platform/infra | `ec2:Create*`, `ec2:Delete*` (VPC/subnets/TGW/NAT), `wafv2:*`, `ecr:*`, `autoscaling:*` |
| workloads | `rds:*`, `elasticache:*`, `mq:*`, `secretsmanager:*` |
| foundation fin_ops | `budgets:*`, `ce:*`, `sns:*` |
| IAM | `iam:CreateInstanceProfile`, `iam:AddRoleToInstanceProfile` |

### Fix
Created policy version v3 on `for-payflow-terraform-dev` covering all required services. Verified with:
```bash
aws iam get-policy-version \
  --policy-arn arn:aws:iam::725094769583:policy/for-payflow-terraform-dev \
  --version-id v3
```
